# Head-to-head market-making replay

This is an experimental research simulator for a **single binary market**. It supports a driver head-to-head contract or one driver's YES token in a race-winner event. These are different questions: a driver's probability of beating another driver is not their probability of winning the race. Market descriptions, timing, and actual resolution rules must be checked for each event. For example, some head-to-head contracts may resolve to 0.5.

For a winner contract, replace `pair` with `instrument: { type: 'race-winner', driver: 'Driver A', race: 'Example Grand Prix' }` and provide `fairValue: { probability: 0.20, asOf: 1759999000000 }`. The probability must be a forecast of the token's expected payout, available at `asOf`; the simulator cannot verify its training or data provenance. No order is submitted before `asOf`. The quote joins the observed best bid and ask subject to at least `minimumEdgeTicks` (default 1) of distance from fair value; inventory skew can move it farther away. This is one token's binary book, not a joint replay of all race-winner outcomes: shared funds, correlated positions, and negative-risk conversion or merging between different drivers are not modeled. Feed a separately frozen forecast and the historical book for each contract. Never use a race result or a later model snapshot as its fair value.

The simulator is an intentionally small fallback while no verified market data has been supplied. The synthetic test cases demonstrate mechanics, **not historical or expected trading performance**. For deeper research, use a purpose-built engine with a suitable feed adapter, such as [NautilusTrader](https://github.com/nautechsystems/nautilus_trader) or [hftbacktest](https://github.com/nkaz001/hftbacktest). No simulation can recover queue position, book depth, or spread from trade prices or candles alone. NautilusTrader's [data requirements](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/data-and-venues.md) and [fill-model documentation](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/fill-prices-and-matching.md) explain the execution-data limitations.

## Interface

`replayMarket(input, options)` accepts a plain JavaScript object. Timestamps are Unix milliseconds UTC. Each replay represents **one token in one market**, ordered by feed receipt time. Its paired driver is implied by the contract and market rules. The initial state holds a funded complete set of YES and NO tokens, and a separate cash balance. The reported position is the change in YES shares relative to that initial set; profit is measured relative to the initial complete sets plus cash. Data should include all received L2 price-level updates and trade prints; an L2 snapshot is required before any updates or trades.

```js
{
  pair: { driverA: 'Driver A', driverB: 'Driver B' },
  firstPractice: 1760000000000,
  exitTime: 1759999999000, // strictly before firstPractice
  exitMode: 'settlement', // alternatively 'liquidation'
  settlement: 0.5,        // required only in settlement mode: 0, 0.5, or 1
  coverage: { start: 1759999000000, end: 1759999999000, complete: true },
  events: [
    { type: 'snapshot', timestamp: 1759999000000, bids: [[0.45, 20]], asks: [[0.55, 30]] },
    { type: 'update', timestamp: 1759999001000, side: 'buy', price: 0.45, quantity: 15 },
    { type: 'trade', timestamp: 1759999002000, side: 'sell', price: 0.45, quantity: 18 },
  ],
}
```

A snapshot replaces the entire book. Updates contain **absolute** size, with zero deleting a level. Trade `side` denotes the aggressor; a sell trade consumes the bid queue. Prices are token prices between zero and one and quantities are shares. Event timestamps must be nondecreasing; ties preserve input order. If an event carries `sourceTimestamp`, the replay additionally rejects a source time after receipt, a source-to-receipt delay above `maxSourceAgeMs`, or source timestamps that move backward. Such delays and disorder can make a newly received snapshot older than already seen updates. This is a conservative filter: an old source time is not proof that a quiet-market book is stale, and source timestamps need not represent the exchange's true event sequence. The monotonicity check rejects decreases in the supplied source timestamps but cannot prove correct ordering or continuity. Sources without source timestamps cannot receive these checks and need independent validation. A `gap` event causes an error. `coverage.complete` is a caller attestation that the initial snapshot and all relevant updates and trades were captured without known gaps through `exitTime`, not proof of completeness. A converter must reject a missing initial snapshot, interrupted capture, absent hourly files, or otherwise unverified coverage; setting this flag without establishing it invalidates results. Events after the exit are ignored.

Defaults: `tickSize: 0.01`, `orderSize: 5`, `maxInventory: 10`, `inventorySkewTicks: 0.1`, `latencyMs: 1000`, `maxBookAgeMs: 60000`, `maxSourceAgeMs: maxBookAgeMs`, `feeMode: 'flat'`, `makerFeeRate: 0`, `takerFeeRate: 0`, and `liquidationSlippageTicks: 1`, `initialCompleteSets: maxInventory`, and `initialCash: 2 * maxInventory`. The initial complete sets and cash must be funded upfront; the implied starting capital is their sum in collateral units. In the default `flat` mode, fee rates are fractions of notional. In optional `polymarket` mode, set `feeMode: 'polymarket'` and explicitly supply the historical market's `takerFeeRate`; maker fees are zero and taker fee is `shares * takerFeeRate * price * (1 - price)`, per [Polymarket's fee documentation](https://docs.polymarket.com/trading/fees). A nonzero `makerFeeRate` is rejected in that mode and no maker rebate is assumed. Market categories and fee schedules change over time; the caller must supply the applicable historical rate rather than applying a current rate retroactively. Fees are debited in cash here, an approximation of venue mechanics. Set `maxBookAgeMs` using the source's actual reliability characteristics. Full fills and fees are returned; `profit` is null when liquidation cannot flatten the position.

## Execution model and limitations

- At each feed event, quote the observed best bid and ask, skewing both by inventory and keeping the position within `maxInventory`. New quotes activate after the configured latency and are rejected if they would cross the then-current opposing quote. Cancellation and requoting are immediate, with no cancel latency.
- On activation, every displayed share at the same price is assumed ahead of the simulated order. Only a subsequently reported aggressor trade at **exactly** the quote price consumes that queue and can fill it. Book-size changes do not advance the queue or generate fills, so the same reported execution is not counted once as a book change and again as a trade. Queue ordering within an L2 level and cancellation priority are unknown. The model does not fill on trades through the quote or crossed-book updates, which can omit adverse fills and bias results. Real venue matching and recording order may differ. On a complete fill, the same side is not replenished until another book update arrives.
- The simulator does not alter historical observations when it fills. It assumes the hypothetical order is small enough not to affect later observed activity; historical book and trade quantities may already overlap. Snapshot and update ordering, duplicate trade prints, lost events, and timing differences can all cause errors. This is not a calibrated exchange simulator.
- For `liquidation`, resting orders are canceled and inventory is closed at `exitTime` by walking displayed depth, with the specified additional price slippage and taker fee. After a reported trade, displayed depth at that price is excluded from liquidation until a subsequent absolute level update or snapshot refreshes it, avoiding reuse of potentially consumed liquidity. If the book is stale, crossed, too shallow, or cannot supply an executable price, `complete` is false and `profit` is null. For `settlement`, no post-cutoff orders or fills occur: residual inventory pays the explicitly supplied final value. Settlement is used only for reporting, never for quote decisions. Unlike liquidation, settlement mode retains race exposure.
- Before quoting, cash limits bids and owned YES tokens limit asks; liquidation buys are also cash-limited. The initial YES and NO shares are assumed to have been created by funding complete sets, and initial capital is not free. A negative position is relative to the initial YES holdings, not a naked short. Initial cash and complete sets are reported so returns can be calculated against funded capital. Only one bid and one ask can be active, so the bid is the sole resting cash reservation. The simulator does not model real splitting, redemption, exchange allowances, changing collateral requirements, minimum order sizes, funding cost, or venue-specific fee schedules. Fractional fills, fixed per-notional fees, timestamps, tick sizes and latency are simplifications; this is not a Polymarket execution implementation or evidence of executable returns.
- Only supplied events at or before `exitTime` enter the strategy, and `exitTime` must be strictly earlier than FP1. Event inputs and all model parameters must be selected without using future outcomes. The caller is responsible for a reliable, timezone-aware FP1 timestamp and for excluding any earlier relevant session if required. Use separate historical events for parameter selection and evaluation; report coverage, sample sizes, inventory, fees, unfilled orders, and sensitivity to queue and execution assumptions.

Run mechanics and invalid-input tests with `node tests/test-market-making-replay.mjs`.

To run the included synthetic demonstration and inspect its simulated fills and profit:

```sh
node research/prediction-markets/backtest/run.mjs research/prediction-markets/backtest/synthetic-example.json
```

The JSON document contains `input` and optional `options` objects as described above. The synthetic classification is an input label; the program cannot authenticate the source or establish that it is historical. Its printed example profit is entirely invented to exercise the execution logic. To run another dataset, supply a document of the same shape and set coverage to complete only after independently checking the capture.

## Forecast integration assessment

The repository already has `forecastPreWeekend` in `packages/core/src/forecast/head-to-head.js`, which uses the pre-weekend mode without same-weekend qualifying or grid inputs. It is **not used by this strategy**: its underlying `forecastPair` reads the model's latest state, and applying today's `data/model*.json` to a historical market would leak later race results. The forecast also predicts the project's pace/finishing-order benchmark conditional on its observation coverage, whereas an exchange contract settles under its specific rules. These targets can differ when drivers retire, are unclassified, withdraw, or the market resolves to a half payout.

A safe integration requires, for each historical quote window:

1. Freeze the model state, feature values, head coefficients, driver/team mapping and their source-data publication times as actually available before the quote. Record a creation timestamp and a checksum. Reconstructing an old date from a later published model is insufficient; verify training and hyperparameter selection also exclude future races.
2. Map the contract's exact question and YES token to the same drivers and race, and capture the complete contemporaneous resolution and void rules. Estimate the market's **expected payout**, including the probabilities of 0, 0.5, and 1, rather than assuming the benchmark's pairwise probability equals token value. A separately validated, strictly historical calibration is needed for any mapping.
3. Publish each forecast with `asOf` and provenance and expose it only to events at or after `asOf`, before FP1. Reject a model whose latest training or feature timestamp is later than `asOf`; never use settlement when forming a quote. Evaluate the resulting signal on later untouched races, alongside an otherwise identical market-only strategy.

Until these inputs and checks exist, shifting quotes toward the existing latest-model output would create unsupported accuracy and look-ahead claims, so the replay quotes the observed book only.
